# (SimpleResilientPaymentScenario)

## 1. هدف و خلاصه

این پروژه ابتدا سناریوی ساده‌ی پرداخت (ثبت پرداخت در دیتابیس ← فراخوانی بانک ← ذخیره‌ی نتیجه) را دقیقاً همان‌طور که در صورت تسک آمده پیاده‌سازی می‌کند و سپس آن را در برابر خطاهای رایج محیط Production مقاوم می‌کند.

- **تکنولوژی:** ASP.NET Core Web API روی .NET 8، EF Core 8، SQL Server (LocalDB)
- **بانک:** با `FakeBankClient` شبیه‌سازی شده است.

---

## ۲. ساختار پروژه
ساختار «شبه Clean Architecture» با دو لایه‌ی `Domain` و `Infrastructure` است. عمداً لایه‌ی `Application` جدا نساخته‌ام، چون برای تسکی با یک Use Case، پیچیدگی اضافه‌ای بود.

## ۳. رفتار سیستم در 6 سناریوی خواسته‌شده

| # | سناریو | رفتار سیستم | نتیجه برای کلاینت |
|---|--------|-------------|-------------------|
| 1 | دو درخواست کاملاً یکسان همزمان | هر دو `INSERT` می‌زنند؛ Unique Index فقط یکی را می‌پذیرد. برنده بانک را صدا می‌زند، بازنده خطای Unique را می‌گیرد و رکورد برنده را می‌خواند. | برنده: `200`. بازنده: `409` (در حال پردازش). فقط **یک** فراخوانی بانک. |
| 2 | درخواست قبلی موفق شده ولی کلاینت پاسخ را نگرفته و Retry می‌کند | رکورد موجود پیدا می‌شود، داده یکسان است و وضعیت نهایی شده؛ **نتیجه‌ی ذخیره‌شده** برگردانده می‌شود و بانک صدا زده نمی‌شود. | `200` با همان `paymentId` (Idempotent) |
| 3 | `OrderId` یکسان با `Amount` یا `CustomerId` متفاوت | داده‌ی درخواست با رکورد ذخیره‌شده مقایسه می‌شود؛ تفاوت یعنی درخواست متفاوتی با کلید تکراری آمده. هیچ‌چیز تغییر نمی‌کند و بانک صدا زده نمی‌شود. | `409` عنوان «Payment conflict» |
| 4 | بانک انجام داده ولی سرویس قبل از ذخیره‌ی نتیجه Crash کرده | رکورد `Pending` می‌ماند. Retry هرگز بانک را دوباره صدا نمی‌زند (چون `INSERT` شکست می‌خورد). Job پس‌زمینه (طراحی شده، **پیاده‌سازی نشده**) بعد از `BankTimeout + Grace` آن را `Unknown` می‌کند. | `409` برای درحال اجرا یا تایم اوت تمام شده |
| 5 | چند Instance همزمان | هماهنگی فقط از طریق دیتابیس است (بدون Lock یا حافظه‌ی مشترک در برنامه) ← رفتار دقیقاً مثل سناریو 1. | مثل سناریو 1 |
| 6 | Timeout ارتباط با بانک، نامشخص بودن نتیجه | فراخوانی بانک با Timeout خودمان (5 ثانیه) محدود شده. هر خطای بدون پاسخ قطعی ← وضعیت `Unknown` ذخیره می‌شود. **هیچ Retry‌ای به بانک زده نمی‌شود.** | `409` عنوان «Payment status unknown» با راهنمای «با OrderId جدید تلاش نکنید» |

## ۴. Idempotency:

چون در توضیحات تسک بیان شده بود که `OrderId` توسط سیستم درخواست کننده تولید میشود و شناسه همان سیستم است. من در این پیاده سازی آن را یک Idempotent key در نظر گرفتم.

سه جزء با هم کار می‌کنند:

ابتدا **Unique Index روی `OrderId` (تضمین):** دیتابیس، به‌صورت اتمیک و حتی زیر همزمانی بالا، اجازه می‌دهد حداکثر یک رکورد برای هر `OrderId` وجود داشته باشد. این تضمین را هیچ کدی در سمت برنامه نمی‌تواند بدهد.

سپس **Insert-First (قفل):** به‌جای «اول بررسی کن، بعد ثبت کن»، **اول ثبت می‌کنیم** و فقط درخواستی که `INSERT`اش موفق شده اجازه‌ی صدا زدن بانک دارد. رکورد `Pending` همزمان نقش «رکورد Idempotency» و «قفل» را دارد.

و سپس **Replay (بازپخش نتیجه):** درخواستی که `INSERT`اش شکست خورده، رکورد موجود را می‌خواند. اگر داده یکسان باشد و پرداخت تمام شده باشد، همان نتیجه‌ی ذخیره‌شده را برمی‌گرداند.

**چرا صحیح است؟** چون حداکثر یک `INSERT` موفق برای هر `OrderId` وجود دارد و فراخوانی بانک فقط بعد از `INSERT` موفق انجام می‌شود، پس:

> **به ازای هر `OrderId` حداکثر یک فراخوانی بانک اتفاق می‌افتد؛ مستقل از تعداد Retry، میزان همزمانی و تعداد Instanceها.**

## ۶. تغییرات طراحی API

 قرارداد `POST /api/payments` تغییر نکرده است. پاسخ‌های خطا برای تمیزی بیشتر کد با `ExceptionHandler` هندل میشوند و با `ProblemDetails` (RFC 7807) و کد `409` برگردانده می‌شوند و با `Title` از هم تفکیک می‌شوند:

| حالت | HTTP | Title |
|------|------|-------|
| تمام‌شده یا Replay | 200 | — |
| پرداخت دیگری با همین OrderId در حال پردازش است | 409 | Payment in progress |
| همین OrderId با داده‌ی متفاوت | 409 | Payment conflict |
| وضعیت پرداخت نامشخص است | 409 | Payment status unknown |

## ۷. مدیریت Concurrent Requestها و چند Instance

- هماهنگی فقط از طریق **Unique Index دیتابیس** است. از `lock`، `SemaphoreSlim`، دیکشنری Static یا `MemoryCache` برای تشخیص تکراری بودن استفاده نشده؛ چون این‌ها فقط داخل یک پروسس کار می‌کنند و در چند Instance متفاوت کارایی ندارند.
- وضعیت «در حال پردازش» هم در دیتابیس (`Pending`) ذخیره می‌شود، نه در حافظه، پس همه‌ی Instanceها آن را یکسان می‌بینند.

---

## ۸. مدیریت Retry و Timeout

برای **Retry از سمت کلاینت (ایمن است):** چون سرور Idempotent است، کلاینت می‌تواند با همان `OrderId` هر چند بار Retry کند و هیچ‌وقت پرداخت دوباره انجام نمی‌شود.

برای **Retry از سمت سرور به بانک (انجام **نمی‌شود**):** عمداً Retry خودکار به بانک نداریم. دلایل:

- این عملیات انتقال پول است و رفتار بانک برای `OrderId` تکراری مشخص نیست (ممکن است پرداخت دوباره انجام دهد).

برای **Timeout:** فراخوانی بانک با یک `CancellationTokenSource` به‌مدت 5 ثانیه محدود شده است.

**نکته**

 **توکن درخواست HTTP به سرویس بانک داده نمی‌شود.** قطع اتصال کلاینت نباید فراخوانی بانک را وسط کار قطع کند.
به همین دلیل **ذخیره‌ی نتیجه بعد از بانک با `CancellationToken.None` انجام می‌شود.** بعد از فراخوانی بانک ممکن است پول جابه‌جا شده باشد و این ذخیره تنها ثبت نتیجه است؛ نباید با قطع یا کنسل شدن از توکن HTTP کلاینت متوقف شود. درواقع قبل از فراخوانی بانک کنسل شدن بی‌خطر است (هنوز اتفاق غیرقابل‌برگشتی نیفتاده)، پس `INSERT` اول با توکن واقعی انجام می‌شود.

## ۹. مدیریت وضعیت‌های نامشخص (`Unknown`)

**چرا وضعیت جدا؟** `Failed` یعنی «مطمئنیم بانک پرداخت نکرده». `Unknown` یعنی «نمی‌دانیم». اگر Unknown را `Failed` بگیریم و کلاینت دوباره پرداخت کند، مشتری دو بار شارژ می‌شود.

**دو راه رسیدن به `Unknown`:**

اول **Timeout یا خطا در همان درخواست (پیاده‌سازی شده):** پروسس زنده است و می‌داند نتیجه نامشخص است، پس بلافاصله `Unknown` را ذخیره می‌کند و به کلاینت پیام می‌دهد.

دوم **Crash (طراحی شده، پیاده‌سازی نشده):** راه‌حل، یک **Background Job** است که پرداخت‌های `Pending` قدیمی‌تر از `BankTimeout + Grace` را به `Unknown` تبدیل می‌کند.

**پیام به کلاینت:** پیام `409` صریحاً می‌گوید وضعیت نامشخص است و **نباید با `OrderId` جدید دوباره تلاش شود**، چون ممکن است پرداخت قبلی انجام شده باشد.

### طراحی Job پس‌زمینه (پیاده‌سازی نشده)

برای زمانی که درخواستی به دلیل کرش کردن سیستم در حالت pending رها میشود میتوان یک بکگراند جاب پیاده سازی کرد تا بعد از ریست شدن یا حتی بصورت دوره ای درخواست هایی که در حالت pending هستند و زمان timeout شان نیز تمام شده را به unknown تغییر دهد.


### رفع وضعیت `Unknown` (Reconciliation)

وضعیت `Unknown` وضعیت پایانی نیست. باید با **استعلام از بانک** (در صورت وجود API استعلام بر اساس `OrderId`) یا **گزارش تسویه‌ی بانک** به `Succeeded` یا `Failed` تبدیل شود، به‌صورت دستی یا با یک Job. این کار فعلاً **پیاده‌سازی نشده** است چون جزئیات API بانک در دسترس نبود.

## ۱۰. تصمیمات معماری و Trade-offها

| تصمیم | جایگزین بررسی‌شده | دلیل انتخاب و هزینه‌ی آن |
|-------|--------------------|--------------------------|
| Unique Index + Insert-First | | ساده‌تر است، وابستگی جدید ندارد و تضمین اتمیک دیتابیس را دارد. هزینه: دیتابیس نقطه‌ی هماهنگی است و Throughput نوشتن به آن وابسته است. |
| **بدون صف** برای پردازش | صف (RabbitMQ) برای جلوگیری از پردازش تکراری | صف‌ها ممکن است خود یک پیام را بیش از یک بار تحویل دهند و باز هم به Unique Index و idempotency نیاز دارند و حالت‌های خطای جدید اضافه می‌کند. |
| بدون Retry به بانک | Retry | خطر پرداخت دوباره. |
